Basic LLM Application Pattern

The simplest production pattern: client applications interacting synchronously or via server-sent events (SSE) with an LLM inference API through structured input/output validation.

Core System Components:
Client Frontend (Next.js / React / Mobile UI)Backend API Gateway (Express / FastAPI / Next.js Route Handler)Prompt Template & Sanitization LayerLLM Provider API (OpenAI / Anthropic / Groq / vLLM)Schema Validator (Zod / Pydantic)
End-to-End Data Flow:
1
User Input Transmission

User enters text into client UI; frontend dispatches authenticated POST request to backend API.

2
Sanitization & Parameterization

Backend validates payload, checks rate limits, and injects user input into a static system prompt template.

3
Inference Invocation

Backend calls external LLM provider over HTTPS with temperature, max_tokens, and streaming flags.

4
Token Streaming & Validation

Tokens stream back through backend via SSE to client, while backend verifies JSON schema compliance.

Execution Actors & Operations:
StepActor / ComponentAction Performed
01End UserSubmits prompt query in the browser interface
02Backend GatewayAuthenticates user session, checks token rate limits, and applies prompt template
03LLM EngineExecutes autoregressive token sampling and streams output tokens
04Schema ParserValidates structural schema integrity before finalizing UI state
Architectural Security Considerations:
  • •Never expose LLM API secret keys in client-side frontend code
  • •Implement strict token usage budgets and rate limits per user to prevent denial-of-wallet attacks
  • •Sanitize prompt inputs to prevent prompt injection from breaking out of delimiter boundaries

Production Hybrid RAG Architecture

An enterprise-grade document retrieval architecture combining dense vector semantic search, sparse BM25 keyword search, reciprocal rank fusion, and cross-encoder reranking.

Core System Components:
Document Ingestion Worker (Unstructured / PyPDF / Markdown splitter)Vector Embedding Engine (Text-embedding-3-large / BGE-large)Hybrid Vector Store (PostgreSQL with pgvector / Qdrant / Pinecone)Query Transformation & HyDE ModuleCross-Encoder Reranker (Cohere Rerank / BGE-Reranker)Foundation LLM Generator (Claude 3.5 Sonnet / GPT-4o)
End-to-End Data Flow:
1
Document Ingestion & Chunking

Documents are parsed, cleaned, split into 500-token semantic chunks with 50-token overlap, and assigned unique UUIDs and metadata.

2
Embedding & Hybrid Indexing

Dense embeddings are computed and stored in an HNSW vector index; text chunks are simultaneously indexed in a BM25 sparse index.

3
Query Expansion & Dual Search

User query generates dense query vector and sparse tokens. System retrieves top 50 dense candidates and top 50 sparse candidates.

4
Reciprocal Rank Fusion & Reranking

Results are fused and passed through a neural Cross-Encoder reranker to extract the top 5 highest-relevance passages.

5
Grounded Synthesis

The 5 passages are formatted into the prompt context with strict citation instructions; LLM generates verified response.

Execution Actors & Operations:
StepActor / ComponentAction Performed
01Client UserSubmits domain-specific technical question
02Query EngineApplies query rewriting and dispatches parallel dense + sparse vector lookups
03Cross-EncoderComputes deep attention scores between query and all candidate passages
04LLM GeneratorSynthesizes grounded output citing chunk source IDs strictly
Architectural Security Considerations:
  • •Implement strict Access Control Lists (ACLs) so users cannot retrieve document chunks they lack permission to view
  • •Sanitize document chunks during ingestion to mitigate indirect prompt injection attacks hidden inside PDFs
  • •Log retrieved chunk IDs to enable auditing of compliance claims and hallucinations

Tool-Using ReAct Agent Architecture

A cognitive state machine where an LLM alternates between internal reasoning traces (thoughts) and external environment actions (API tool calls) until a goal is accomplished.

Core System Components:
Agent Orchestrator / State Machine (LangGraph / native loop)Model Context Manager (Working memory + conversation history)Tool Registry (Typed JSON schemas for search, SQL, bash, calculation)Isolated Execution Sandbox (Docker container / Firecracker microVM / WebContainer)Safety Guardrail & Permission Interceptor
End-to-End Data Flow:
1
Goal Specification

User supplies a high-level task with constraints.

2
Reasoning & Tool Selection

Model processes conversation state and tool definitions, generating a <thought> and a structured tool invocation request.

3
Sandbox Execution

Orchestrator parses tool arguments, validates permissions against security rules, and dispatches call inside an isolated sandbox.

4
Observation Ingestion

Execution output (stdout, error, API JSON) is captured and appended to the context as an Observation.

5
Evaluation & Termination

Model inspects observation. If task is complete, it outputs final answer; if incomplete or errored, it self-corrects and iterates.

Execution Actors & Operations:
StepActor / ComponentAction Performed
01UserIssues high-level operational goal
02Agent BrainEvaluates state, writes reasoning thought, and yields tool call payload
03Sandbox RuntimeSafely runs tool command and returns stdout/stderr
04Agent BrainAnalyzes outcome and decides next step or final synthesis
Architectural Security Considerations:
  • •Isolate all bash and filesystem operations inside disposable containers with no host network access
  • •Never allow the agent to execute unconstrained SQL drop/delete commands without human approval
  • •Enforce hard limits on maximum loop iterations and maximum token expenditure

Zero-Cloud Local AI Assistant

A fully offline, privacy-preserving AI system running completely on consumer workstation hardware with local quantized models, embedded vector storage, and zero data telemetry.

Core System Components:
Local Desktop Client / CLI InterfaceLocal Model Runtime (Ollama / llama.cpp)GGUF Quantized Model Checkpoint (e.g. Llama-3.3-70B-Q4 or Qwen-2.5-Coder-32B)Embedded Vector Database (ChromaDB / LanceDB / DuckDB)Local Document Parser & Sentence Transformer
End-to-End Data Flow:
1
Local File Indexing

User selects local directories; local Python/Node script parses text files and runs a compact local embedding model (e.g. all-MiniLM-L6-v2).

2
Embedded Storage

Embeddings and metadata are written directly to an on-disk SQLite or Arrow file with no remote server.

3
Local Query & Retrieval

User enters question; local vector distance calculation runs in milliseconds in embedded memory.

4
On-Device Generation

Ollama loads quantized model into local GPU VRAM or unified memory (Apple Silicon Metal) and streams response.

Execution Actors & Operations:
StepActor / ComponentAction Performed
01Local UserInputs query through terminal CLI or local desktop app
02Embedded Vector DBPerforms nearest neighbor search entirely in local memory
03Ollama RuntimeExecutes quantized tensor math on local GPU/NPU
04Local UIRenders response locally with zero network packets emitted
Architectural Security Considerations:
  • •Guarantees total data privacy: zero risk of cloud data leakage, IP exposure, or third-party training ingestion
  • •Verify SHA256 checksums of all downloaded GGUF model files to prevent malicious weight tampering
  • •Bind local API endpoints strictly to localhost (127.0.0.1) rather than public network interfaces (0.0.0.0)
